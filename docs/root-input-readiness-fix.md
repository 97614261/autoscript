# 按键能力读取修复

## 原因与边界

Root 已连接后，后台工作线程会在宿主事件队列上休眠。JNI 的输入能力查询只向独立控制队列发送 `InputFeatures`，遗漏宿主队列唤醒，导致没有脚本请求时查询超时并返回 0。编辑器据此禁用所有按键动作；这不能证明设备没有 Root 权限。

修复查询发送后立即唤醒工作线程，保留原有五秒超时、队列上限和未连接时返回 0 的保护。不引入轮询、不绕过 Root 握手、不放开未确认支持的动作。

两个编辑器宿主使用 nullable 能力值区分读取中与真实不可用，连接阶段变化时重新读取。客户端拒绝跨服务或跨会话返回的过期能力值。

## 验证

- Rust 回归：空闲工作线程无脚本业务请求时，连续 20 次查询通过事件唤醒取得能力；断开的控制通道不能返回虚假能力。
- Studio 回归：读取中、无输入能力、基础输入与持续单指能力分别判断。
- MuMu 只读诊断：`su` 返回 UID 0，以智构应用 UID 调用也通过；Runner 服务存在，随机名称的守护进程以 root 身份运行。初次仅筛选应用名称漏掉了该进程，已扩大筛选并确认。不能仅凭本次源码修复声称实机按键执行已验证。
- 未执行用户脚本或自动点击目标应用，未清除应用数据。

本批验证结果：Rust engine-jni 27 项通过；Studio 264 项、runtime-client 13 项通过；runtime-service 51 项中 50 项通过、1 项既有平台条件跳过。`cargo fmt --all -- --check` 通过，Clippy 非严格检查通过但保留既有警告；`-D warnings` 被 root-protocol 既有警告阻断，未扩大本批修改范围。`build.cmd -Verify` 成功，Lint 无 Error（33 Warning、16 Hint），MuMu 0 更新安装成功，应用数据保留。设备实际选点/执行仍由用户验证。
