# Root 截图和 Rust 找图性能优化

架构决定：[ADR 0048](../../../../docs/adr/0048-bounded-fast-root-capture-and-exact-template-prefilter.md)。不改变项目数据、原像素、相似度、透明策略、搜索顺序和找到/未找到语义。

## 已实现

- 协议 v3 协商认证流式截图：720×1280 RGBA 原来需要 60 次像素分块请求，现在一次 CaptureStream 请求推送元数据及 60 个有界像素包。仍逐包验证 HMAC、序号、请求身份和偏移，64 MiB 帧上限不变。不支持的旧端仍走原 Capture/Chunk 链路。
- 独立常驻 Root app_process 截图桥，使用系统 SurfaceControl/ScreenCapture 获取当前显示器原尺寸画面，不通过图片文件传输；软件位图读回仍有拷贝，不宣称零拷贝。默认不包含安全/受保护图层。桥与输入进程隔离，退出释放位图、硬件缓冲和管道。
- 隐藏接口不兼容或桥失败时，禁用本连接的桥并使用既有 screencap。单次桥与回退共用 5 秒采集上限，停止能打断采集；流式传输有截止时间和背压，异常/半帧后连接作废，不能将部分像素当成功帧。
- Debug 构建优化协议/哈希/视觉热路径，仍保留 Debug 签名、溢出检查和鉴权。
- Rust 主色积分预筛：只排除数学上不可能达到原阈值的窗口，幸存窗口仍执行原逐像素精确评分。没有跳点近似或偷偷降低相似度。积分表最多 8 MiB，构建与遍历使用同一取消、超时及比较预算；小区域、严格阈值和不适合的多色模板走原路径。
- 日志分别记录采集、认证传输、帧入池及总体宿主往返；标注真实后端，避免快速桥和兼容链路混算。

## 合成基准（不是模拟器/项目实测）

主机 Windows x86_64，Intel Core Ultra 9 285H；Rust 开发配置、pixel-vision opt-level=3。帧 720×1280，ROI 全屏 [0,0,720,1280]，模板 32×24、单一主色，精确容差，相似度 900‰，RGBA，左上起步长 1，结果未找到，100 次。基线仅禁用新增积分预筛，其余评分、缓存及配置相同。

## 2026-10-06 第二轮：减少桥调用和临时分配

- 截图桥从逐行 `getPixels` 改成有界批量读取，每块最多32行、最多16,384像素。720×1280时每块22行，读取调用由1280次降为59次。两块工作数组合计最多128 KiB，复用同尺寸帧工作区；不保留或复用截图内容。最后不足一块时仅写有效字节，不输出旧尾部。
- 继续使用 `getPixels` 的 ARGB 颜色语义，显式转换 BGRA，保留 Alpha；没有改用未经验证的预乘/native字节拷贝。单元测试覆盖每个像素、非整块尾部、透明值、横竖尺寸变化及跨帧复用。
- 客户端 UnixStream 在70 KiB单包长度上限内复用接收 Vec。借用协议载荷完整经过认证、形状、序号检查，客户端再检查请求关联、状态和偏移，之后直接追加到目标帧。一次720×1280截图不再为60个像素包分别创建拥有式载荷 Vec，并省去合计3,686,400字节的这一级载荷复制；仍有桥读回、包读取和目标帧写入，不是端到端零拷贝。
- 读取截断、空包或超大包时清除缓冲有效长度；半帧、鉴权或关联错误继续令流连接作废。旧拥有式解码接口和不支持复用的 PacketTransport 默认实现保持兼容。新增连续两次大帧及中间小包回归，证明接收工作区能够跨包、跨帧复用，而帧像素相互独立。

这些是代码路径和分配次数的变化，不是新增模拟器毫秒实测。没有自动运行私人项目。

## 2026-10-09 截图失败诊断补充

用户反馈 `SCREEN_CAPTURE_FAILED: RootDaemon failed to capture the screen`。这条旧消息合并了后端、传输、协议和帧校验错误，不能据此确认是找图超时，也不能确认第三轮优化就是根因。

在 MuMu 0、Android x86_64、720×1280 上，以 Studio 的实际应用 UID、`su -c` 启动独立诊断会话，使用随机会话密钥和生产 RootClient/RootDaemon，连续 100 次截图及认证分包均成功；每帧 3,686,400 字节，后端为快速截图。没有执行私人项目、输入操作或保存屏幕图像。此结果只说明此条件下没有复现，不排除间歇故障、系统显示切换或其他运行上下文。诊断不用于性能百分位结论。

新增可选 `CAPTURE_FAILURE_DETAILS` 协商位：采集失败最多返回一个4字节白名单原因（采集截止时间、回退进程启动、管道读取、进程退出、帧格式、ID耗尽）。旧客户端收到原来的空错误载荷；客户端仍校验协商、鉴权、状态及请求关联，流式失败仍废弃连接，不使用半帧。JNI仅向脚本错误补充固定错误码，不输出任意异常文本、屏幕内容、路径或密钥。调试弹窗解释截图与匹配的区别，旧日志不伪造原因。

截图回退失败时再检查停止标志，主动停止优先返回取消，不被回退错误覆盖。未扩大5秒采集预算，未自动重试、缓存旧画面或修改识图语义。尚未取得用户原故障的具体失败码，不能声称根因已经修复。

本批验证：Rust相关5个crate测试、格式检查、Clippy及差异空白检查通过（有既有静态检查警告）。`build.cmd -Verify`完整构建成功，Android565项测试通过、1项跳过，Lint无错误、34项警告和14项提示；arm64/x86_64开发包及内嵌Runner构建成功，保留数据更新安装到MuMu 0号实例。独立诊断会话、设备临时二进制和临时源码均已清理。下一步需要用户按原步骤复测；若失败，具体错误码是确认根因的依据。

## 2026-10-09 第三轮：Root发送缓冲和采集分段

Root生产流式路径不再为每个分块创建独立像素Vec、前缀Vec和认证包Vec。直接从已捕获帧复制到会话载荷工作区，编码到可复用包工作区，同步写出后才生成下一包。相比原路径，一帧720×1280省去一层合计3,686,400字节的像素复制，60包不再反复分配三层像素大小的Vec；仍有两个有界工作区及小请求/元数据分配，不宣称零分配或零拷贝。

固定大小、偏移和前缀校验、HMAC、递增序号、请求关联及分块背压继续保留。旧CommandDispatcher默认实现和拥有式包接口兼容保留；生产发送使用直接填充覆盖实现，优先停止栅栏仍在锁内复查。失败/取消/坏前缀/长度错误及时释放截图，编码错误不留下有效包。包编码回归逐字节对比新旧输出，覆盖跨包/跨帧、末块、序号耗尽和取消清理。
